## What I built
- **`supabase/functions/bug-report-retention-purge/`**
  - `index.ts`: the handler. It checks the edge-function secret, then calls the candidate query, runs the purge and records each finished class. It logs and returns counts only.
  - `purge.ts`: the purge logic, kept separate so it can be tested.
  - `purge.test.ts`: unit tests against a mocked Sentry.
  - `retentionPurge.nightly.ts`: the real-Sentry H1–H3 spec.
- **Feedback:** it lists issues matching `issue.category:feedback class_id:"N"` with Link-cursor pagination, then deletes by `?id=` in batches of 100 (Sentry allows 1000; 100 keeps URLs short).
- **Replays: per-id delete, not the bulk job.** The bulk job deletes whatever its query matches on the server, so our own tag check couldn't run first. It also needs a time range and finishes asynchronously, so counts would come from polling. Listing then deleting by id puts the check in front of every delete and gives exact counts.
- **Exact tag match, two layers:**
  - On 26.5, `class_id:N` is an exact match: `class_id:99900` does not match 999001; only a trailing `*` does prefix matching.
  - Independently, each item's own tag values must be exactly `[N]` before it is deleted, and issues must be in the feedback category. So reports without a `class_id` (H3), and class 10's reports when purging class 1, survive even if the search returns them.
- **Failures:**
  - A 429 waits for `Retry-After` (capped at 60 s, 5 tries).
  - 5xx and network errors back off exponentially.
  - 401, 403 or 429s that don't clear stop the run.
  - Classes that fail or don't get reached stay unrecorded and are retried the next day. Each run stops starting new classes after 100 s and handles at most 50.
- **Migration `supabase/migrations/20260929120000_bug_reporter.sql`** (created; I'm the first package to write to it):
  - I added a small state table, `bug_report_retention_purges` (RLS on, no grants to anon or authenticated). It records the last sweep per class, lets a doubled cron call skip classes swept in the last 20 hours, and puts never-swept classes first.
  - Two service-role-only RPCs, `get_bug_report_retention_purge_candidates` and `record_bug_report_retention_purge`.
  - A daily `pg_cron` job at `41 5 * * *`, using `call_edge_function_internal` like the other reconcilers.
  - A class keeps being swept daily for 365 days after its grace period, because reports can still arrive against an archived course. After that the job never queries it again. 365 must stay at or above `sentry.cleanup.days` (about 150).
- **Local DB:** applied the migration under the DB lock, checked the SQL for 29/31 days, null end dates, the 365-day window and the 20-hour skip, confirmed `authenticated` is denied, and ran `npm run client-local`. The types diff contains only my additions.

## Decisions for the human
1. **Class ids collide across deployments sharing the dev Sentry org** (local, CI, staging). A purge from any one of them deletes the others' reports with the same `class_id`. I added the optional `SENTRY_PURGE_ENVIRONMENT` filter (off by default, which matches the spec). It only helps if each deployment sets its own `SENTRY_ENVIRONMENT`; the web SDK otherwise falls back to `NODE_ENV`, typically "production". Prod is a separate install, so it's unaffected.
2. **Token scopes for HU3:** I documented `org:read project:write event:admin`. `org:read` is my addition, in case Sentry's org-level issue and replay lists need it; I couldn't check without the token.
3. **Bulk delete of feedback issues was never exercised** (it returns 403 with the agent token). If Sentry 26.5 refuses bulk delete for feedback issues, it will need a per-issue delete fallback (limited to 5 per 5 s).
4. **Not covered by this job:** reports for classes with no `end_date`, and error events tagged `class_id`. Both are left to Sentry's own cleanup, as ADR 1 says.
